# FraudRuleEngine (sample)

This repository contains a sample Fraud Rule Engine implemented in ASP.NET Core with Entity Framework Core and PostgreSQL. It demonstrates:

- Domain models for transaction events and fraud alerts
- A simple rule engine with pluggable rules
- EF Core repository backed by PostgreSQL
- ASP.NET Core Web API to ingest transactions and retrieve alerts
- Dockerfile and docker-compose to run the API and Postgres for local development

Requirements
- Docker & Docker Compose (for running with PostgreSQL)
- .NET 8 SDK (for local development/build)

Quickstart (with Docker)
1. From the `server/` directory run:

   docker compose up --build

2. API will be available at http://localhost:8080
   - Swagger UI: http://localhost:8080/swagger
   - The database is seeded automatically with demo data on first run (see "Seed Data" below), so
     `GET /api/transactions/alerts` returns results immediately without any manual POST.

Endpoints
- POST /api/transactions
  Accepts a JSON payload matching the TransactionEvent model. Example:

  {
    "accountId": "acct-123",
    "amount": 12000.50,
    "category": 1,
    "metadata": "{ \"note\": \"payment\" }"
  }

  Returns 201 Created and any alerts generated by rules.

- GET /api/transactions/{id}
  Retrieve a stored transaction by id.

- GET /api/transactions/alerts
  Retrieve recent fraud alerts.

Notes on production readiness
- Database schema is managed via EF Core Migrations (see "Database Migrations" below) and applied automatically at startup via `Database.Migrate()`.
- Rules are registered in code. In production you might load rule configuration dynamically (database, admin UI, or feature flags).
- Add authentication, rate limiting, structured logging, metrics, and proper error handling for production use.

Configuration
- The Postgres connection string is read from standard ASP.NET Core configuration under `ConnectionStrings:DefaultConnection`.
- `appsettings.Development.json` contains a working default for local development (`Host=localhost;...`).
- `appsettings.json` (used in Production and other non-Development environments) leaves the value empty by design - never commit real credentials. Supply it via the environment-variable override instead:

    ConnectionStrings__DefaultConnection=Host=postgres;Port=5432;Database=fraud_engine;Username=postgres;Password=postgres

  (double underscore `__` is how ASP.NET Core maps env vars to nested configuration keys). `docker-compose.yml` already sets this for the `api` service.
- If no connection string is resolved, the API fails fast at startup with a clear error instead of silently falling back to a hardcoded value.

Database Migrations
- Migrations live in `FraudEngine.Core/Data/Migrations` and are applied automatically when the API starts (`db.Database.Migrate()` in `Program.cs`).
- To add a new migration after changing entities/`FraudDbContext`, run from `server/`:

    dotnet tool install --global dotnet-ef   # first time only
    dotnet ef migrations add <MigrationName> --project FraudEngine.Core --startup-project FraudEngine.Api --output-dir Data/Migrations

- To apply migrations manually against a database (instead of relying on the automatic startup migration):

    dotnet ef database update --project FraudEngine.Core --startup-project FraudEngine.Api

- To generate a SQL script for a DBA / manual deployment:

    dotnet ef migrations script --project FraudEngine.Core --startup-project FraudEngine.Api -o migrate.sql

Seed Data
- On startup, in the `Development` environment only, [`DbSeeder`](FraudEngine.Core/Data/DbSeeder.cs) inserts ~12 representative
  transactions (across several accounts) and runs each one through the real `RulesEngine` - the same
  code path the API uses for `POST /api/transactions` - so the alerts it produces are genuine, not
  hand-crafted. This is a no-op if the `Transactions` table already has data, so it never runs twice
  or clobbers real data.
- `docker-compose.yml` sets `ASPNETCORE_ENVIRONMENT=Development` for the `api` service specifically so
  a reviewer running `docker compose up --build` gets Swagger UI and this seed data out of the box.
- Seeding is intentionally **not** wired up for `Production` - an environment without `ASPNETCORE_ENVIRONMENT=Development`
  set will start with an empty database, as expected for a real deployment.
- To get a completely fresh seed (e.g. after changing the sample data), wipe the Postgres volume and
  restart: `docker compose down -v && docker compose up --build`.

Running locally without Docker
1. Ensure a PostgreSQL instance is available. The Development default (`appsettings.Development.json`) already points to `localhost:5432` with a `postgres`/`postgres` user, matching `docker compose up postgres`. Override it if needed via the `ConnectionStrings__DefaultConnection` environment variable.

2. From `server/` run:

   dotnet build FraudEngine.Api
   dotnet run --project FraudEngine.Api

Tests
- `FraudEngine.Tests` includes unit tests for the rule engine:
  - `HighAmountRuleTests` - verifies the amount threshold boundary behavior.
  - `RapidTransactionsRuleTests` - verifies the count/window logic using an in-memory `IRepository` test double (`TestDoubles/InMemoryRepository.cs`), so no database is needed to run these tests.
- Run tests from `server/`:

    dotnet test
